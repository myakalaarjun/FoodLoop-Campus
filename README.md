# FoodLoop Campus

FoodLoop Campus is a React/Vite and Express/MongoDB application for coordinating campus food donations, verified community recipients, volunteer pickups, and auditable handovers. The dashboards and impact counts are calculated from persisted MongoDB records; there are no fallback or fabricated live metrics.

## Project layout

- `frontend/` — React, Vite, Tailwind CSS, responsive UI, and API client.
- `backend/` — Express REST API, Mongoose models, role middleware, controllers, and matching/audit services.
- `backend/test/` — Node.js test-runner tests for match scoring and eligibility rules.

## Requirements

- Node.js 20+ and npm.
- MongoDB Atlas database (or a MongoDB replica-set deployment). A local standalone MongoDB instance works for the basic application; Atlas is recommended.

## Configure and run

1. For **persistent data**, in `backend/`, copy `.env.example` to `.env` (PowerShell: `Copy-Item backend/.env.example backend/.env`). Set:
   - `MONGODB_URI` to your MongoDB Atlas connection string. Replace the sample username, password, and cluster with your own values; URL-encode special characters in credentials.
   - `JWT_SECRET` to a unique random secret at least 32 characters long.
   - `CLIENT_ORIGIN` to the frontend origin (default `http://localhost:5173`).
2. In `frontend/`, copy `.env.example` to `.env` and set `VITE_API_URL` if the API is not at `http://localhost:4000/api`.
3. Install packages from the workspace root: `npm install`, `npm install --prefix backend`, and `npm install --prefix frontend`.
4. Start both servers with `npm run dev` from the workspace root. The UI is at `http://localhost:5173`; the API health endpoint is `http://localhost:4000/api/health`.

For local development only, if `MONGODB_URI` is not set and `NODE_ENV` is not `production`, the backend starts a real temporary MongoDB server automatically. This mode requires no Atlas credentials, but **all users, listings, and reservations are erased when the backend stops**. A local-only JWT secret is generated by the app for this development mode. For persistent data and production, configure Atlas and a unique `JWT_SECRET` (at least 32 characters); production startup refuses to run without both. Configure Atlas network access and a database user with only the permissions needed for the FoodLoop database. No credentials are committed or bundled into the application.

If the browser reports that it cannot reach the API, check that the backend server is running on port 4000. If it exits at startup, configure the missing `MONGODB_URI` and `JWT_SECRET` in `backend/.env`; the frontend does not mock registration or database operations.

## Fictional demo data

To create repeatable fictional donor, verified-recipient, volunteer, and listing records:

1. Set `DEMO_PASSWORD` in `backend/.env` to a unique password of at least 12 characters.
2. Run `npm run seed --prefix backend`.
3. Sign in using `jamie.donor@example.test`, `morgan.recipient@example.test`, or `sam.volunteer@example.test` with that password.

The seed creates no administrator and does not overwrite existing demo users or delete data. Seed data is clearly fictional. Do not use the demo password outside local development.

## Administrator provisioning

Public registration rejects the `admin` role. Create and verify an administrator out-of-band: register the intended account through the normal flow, then have a trusted database operator promote that exact account after verifying its identity. For example, in `mongosh` connected to the FoodLoop database:

```javascript
db.users.updateOne(
  { email: "trusted-admin@your-organization.example", role: { $ne: "admin" } },
  { $set: { role: "admin", active: true } }
)
```

Review the `matchedCount` and `modifiedCount` result; do not expose database credentials or create a shared default administrator account. Administrators can thereafter manage roles and account activation from the protected dashboard.

## Workflows

- **Donor:** register, maintain profile, publish/edit/cancel food listings (quantities default to meals), inspect reservations, assign an available volunteer, and verify a pickup code.
- **Recipient:** maintain organization name, description, capacity, dietary restrictions, and pickup availability; browse eligible listings ranked by transparent matching components; reserve quantity; cancel reservations; and view history. An administrator must verify the organization before the API will accept reservations.
- **Volunteer:** browse unassigned reservations, view available food listings with donor contact details, coordinate pickup by email or phone, accept a reservation assignment, and verify handover using the recipient's one-time six-digit code.
- **Administrator:** view real usage counts and audit activity, verify recipient organizations, activate/deactivate users, inspect listings, cancel a listing, and manage account roles through the API.

The six-digit code is stored only as a bcrypt hash. It is returned once when the recipient creates the reservation; save it to complete handover. Only the listing donor, assigned volunteer, or administrator may verify it. Verification attempts are rate-limited. Past-deadline available/reserved listings are marked expired and their uncompleted reservations cancelled during dashboard, listing, and reservation reads.

## Matching rules

Eligible matches must have remaining quantity, a future deadline, positive recipient capacity, a feasible pickup time, and no conflict between listing allergens and recipient dietary restrictions. The explainable weighted score uses:

- Pickup feasibility: 35%.
- Capacity relative to listing quantity: 30%.
- Deadline urgency (closer eligible deadlines rank higher): 25%.
- Dietary compatibility: 10%.

For this version, recipient `dietaryNeeds` are treated as ingredients/allergens to avoid and compared case-insensitively with listing `allergens`. Empty pickup availability means flexible availability; otherwise a supplied ISO date-time must fall between the listing's pickup start and deadline. Deadline urgency is `max(0, min(100, 100 - hoursUntilDeadline / 168 * 100))`. The score and component explanations are returned with recipient listing results. Eligibility and capacity are independently checked again by the reservation API. Impact totals count only completed reservations whose declared listing unit is a meal, serving, or portion; other food units are not silently converted into meals.

## REST API

All responses are JSON. Authenticated browser requests use an HTTP-only, SameSite=Strict cookie; Bearer JWTs are also accepted by the API.

| Method | Endpoint | Access | Purpose |
| --- | --- | --- | --- |
| `GET` | `/api/health` | Public | API health |
| `POST` | `/api/auth/register` | Public | Register donor, recipient, or volunteer |
| `POST` | `/api/auth/login` | Public | Sign in |
| `POST` | `/api/auth/logout` | Public | Clear session cookie |
| `GET` | `/api/auth/me` | Authenticated | Current profile |
| `PATCH` | `/api/auth/profile` | Authenticated | Update profile/preferences |
| `GET` | `/api/listings` | Authenticated | Browse listings; recipients receive match explanations |
| `POST` | `/api/listings` | Donor | Create listing |
| `PATCH` | `/api/listings/:id` | Donor owner | Edit an unreserved listing |
| `POST` | `/api/listings/:id/cancel` | Donor owner, admin | Cancel a listing and its active reservations |
| `GET` | `/api/reservations` | Authenticated | Role-filtered reservation history |
| `GET` | `/api/reservations/volunteers` | Donor, admin | List active volunteers for assignment |
| `POST` | `/api/reservations/:listingId` | Verified recipient | Reserve a positive integer quantity |
| `POST` | `/api/reservations/:id/assign` | Volunteer, donor, admin | Accept or assign volunteer |
| `POST` | `/api/reservations/:id/verify` | Donor, assigned volunteer, admin | Verify the pickup code |
| `POST` | `/api/reservations/:id/cancel` | Recipient owner, admin | Cancel an active reservation |
| `GET` | `/api/dashboard` | Authenticated | Role-specific actual-record summary |
| `GET` | `/api/admin/users` | Admin | List users |
| `PATCH` | `/api/admin/users/:id` | Admin | Update account role/activation |
| `GET` | `/api/admin/listings` | Admin | Monitor all listings |
| `PATCH` | `/api/admin/organizations/:id/verification` | Admin | Verify/unverify a recipient |

## Validation and tests

- Run matching rules and eligibility tests: `npm test --prefix backend`.
- Build production frontend assets: `npm run build --prefix frontend`.
- Confirm backend connectivity with `GET /api/health` after the backend reports a successful MongoDB connection.
- For a full local workflow, seed demo records and exercise donor listing, verified-recipient reservation, volunteer assignment, handover verification, dashboard totals, and administrator verification/account controls in separate browser sessions.

The API uses Helmet, an explicit credentialed CORS origin, JSON size limits, general request limiting plus a stricter sign-in and pickup-verification limit, route validation, role/ownership checks, hashed passwords and pickup codes, and audit records for consequential workflows. Use HTTPS in production and set `NODE_ENV=production` so auth cookies are marked Secure.
